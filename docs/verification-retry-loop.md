# 검증 에이전트와 선택적 재처리 로직

- 작성일: 2026-09-02
- 대상: `feat/verification-retry-loop` 브랜치의 현재 프로토타입
- 구현 기준 커밋: `5aeb6f1` (이 문서 추가 전)

## 1. 개요

이 문서는 규제 검토 결과를 검증하고, 발견된 문제에 따라 필요한 도구를 다시 실행하는 로직을 설명합니다.
프로토타입은 LLM이 필요한 규제 도구를 선택하고, 도구 결과를 규칙과 LLM으로 검증하는 구조입니다.

누락이나 오류가 발견되면 관련 도구만 추가 실행하거나 재실행합니다.
정상 도구의 결과는 유지하고, 변경된 결과를 합쳐 전체 초안을 다시 검증합니다.
즉, **재실행 범위는 특정 도구이고 재검증 범위는 전체 초안입니다.**

자동 재처리는 기본 최대 2회입니다. 사용자 입력 필요 상태이거나 검증 자체가 실패한 경우에는
미완료 상태로 종료합니다. 구체적인 상태 우선순위와 종료 조건은 5절과 7절에서 다룹니다.

현재 구현은 누락된 도구 실행, 일시적 도구 오류의 재시도, 이력 보존을 검증하는 프로토타입입니다.
문제 탐지와 문제 해결은 별개의 기능이며, 검증 의견에 맞춰 새로운 검색 전략을 만들거나
제품 정보를 보완하는 자율 수정 기능은 포함하지 않습니다.
규제 도구는 Mock이므로 실제 법적 정확성이나 판매 가능 여부는 검증 대상이 아닙니다.

## 2. 현재 구현 범위와 역할

| 단계 | 담당 | 하는 일 | 현재 범위 |
| --- | --- | --- | --- |
| 입력 | Python | 구조화된 `Product` 로딩 | 미리 정의한 샘플 사용. URL/HTML/이미지 인식은 미구현 |
| 도구 선택 | 규칙 또는 LLM | 6개 도구 각각의 선택 여부와 이유 생성 | LLM 모드에서는 Gemini 호출 |
| 규제 도구 | Python Mock | 도구별 결과, 공통 판단, 필요 조치, 누락 정보 생성 | 실제 정부 API 호출 없음 |
| 종합 | Python | 최신 도구 결과를 `DraftAssessment`로 취합 | 위험도, 조치, 질문을 코드로 생성 |
| 검증 | 규칙, LLM 모드에서는 LLM도 추가 | 누락, 실패, 근거 누락, 모순 등을 검사 | 초안의 완전성·일관성 검토 |
| 재처리 제어 | Python | 재실행 대상 선정, 결과 교체, 횟수 제한 | LLM이 직접 실행 루프를 제어하지 않음 |
| 최종 출력 | Python | 최신 결과와 검증·실행 이력 반환 | CLI 텍스트 또는 JSON |

LLM 분석과 LLM 검증은 같은 모델을 서로 다른 프롬프트로 별도 호출합니다.
여기서 "독립 검증"은 별도의 검토 역할과 규칙 검사를 뜻합니다.
다른 모델이나 외부 전문가가 독립적으로 법적 정답을 확인한다는 의미는 아닙니다.

### LLM에게 보내고 받는 데이터

| 호출 | 입력 | 구조화된 출력 |
| --- | --- | --- |
| 분석 | 제품 JSON, 도구 목록과 설명, 선택 규칙 | 도구별 `tool_name`, `selected`, `reason` |
| 검증 | 현재 전체 `DraftAssessment` JSON, 검토 지침 | `issues`, `additional_tools_required`, `review_summary` |

응답은 JSON Schema를 지정해서 받고 Pydantic으로 다시 검증합니다.
형식 검증이 통과했다고 내용의 사실성까지 보장되는 것은 아닙니다.
최종 검증 상태는 LLM이 반환하는 설명문이 아니라, 규칙 검사와 LLM 응답을 합친 Python 로직으로 계산합니다.

## 3. 최초 실행과 재처리의 차이

### 3.1 최초 실행

1. 샘플 상품을 읽습니다.
2. 분석 에이전트가 실행할 도구를 선택합니다.
3. 6개 도구를 순회합니다. 선택된 도구는 실행하고, 나머지는 생략 기록을 남깁니다.
4. 최신 도구 결과를 모아 전체 초안을 생성합니다.
5. 규칙 검증을 수행하고, LLM 모드라면 Gemini 검토도 수행합니다.
6. 검증 결과에 따라 종료하거나 선택적 재처리로 진입합니다.

선택하지 않은 도구도 `selected=false`, `status=not_applicable`인 결과가 존재합니다.
이는 현재 코드의 실행 생략 표시이지, 해당 규제가 법적으로 적용되지 않는다고 확인했다는 뜻이 아닙니다.
실제 규제 판단을 하는 `run()`은 선택된 도구에 대해서만 호출됩니다.

### 3.2 재처리

1. 검증 결과에서 재실행할 도구를 추출합니다.
2. 해당 도구를 `selected=True`로 실행합니다.
3. 그 도구의 최신 결과만 새 결과로 교체합니다.
4. 다른 도구의 최신 결과는 그대로 유지합니다.
5. 전체 최신 결과를 다시 취합합니다.
6. 전체 초안에 대해 규칙 검증과 LLM 검토를 다시 수행합니다.

이 과정에서 제품 정보는 바뀌지 않고, 최초 LLM 도구 선택도 다시 호출하지 않습니다.
검증 내부에서 규칙 기반 `ToolSelector`로 필요한 도구를 다시 계산하는 검사는 매 회차 수행됩니다.
이 검사는 파이프라인 처음의 LLM 분석을 다시 실행하는 것과 다릅니다.

### 3.3 무엇을 다시 실행하는가

| 구성 요소 | 재처리 시 동작 |
| --- | --- |
| 상품 입력·샘플 로딩 | 다시 수행하지 않음 |
| 최초 LLM 도구 선택 | 다시 호출하지 않음 |
| 재처리 대상으로 지정된 도구 | 실행 |
| 지정되지 않은 도구 | 이전 결과 재사용 |
| 전체 결과 취합 | 다시 수행 |
| 규칙 검증 | 전체 초안에 대해 다시 수행 |
| LLM 검증 | LLM 모드이면 전체 초안으로 다시 호출 |

## 4. 검증 로직 상세

### 4.1 규칙 기반 검사

[verifier.py](../palgijeone/verifier.py)의 `VerificationAgent.verify()`가 수행합니다.

| 검사 | 코드상 조건 | 결과 |
| --- | --- | --- |
| 결과 레코드 누락 | 6개 도구 중 결과가 없는 도구 존재 | `missing_tool`, critical |
| 필요한 도구 미선택 | 규칙상 필요한 도구의 결과가 없거나 `selected=false` | `missing_tool`, critical + 추가 도구 요청 |
| 도구 실패 | 선택된 도구의 상태가 `failed` | `tool_failure`, critical |
| 근거 누락 | 판단이 `required`, `possibly_required`, `not_required`인데 `legal_sources`가 비어 있음 | `missing_evidence`, critical + 판단 ID |
| 판단 모순 | 같은 도구의 판단 집합에 `required`와 `not_required`가 함께 존재 | `contradiction`, critical + 판단 ID들 |
| 핵심 속성 부족 | 제품의 `category` 또는 `intended_use`가 비어 있음 | `insufficient_product_data`, warning |

주의할 점:

- 근거 검사는 현재 출처 목록의 존재를 검사합니다. 원문에 접속하거나 최신성·적용성을 검증하지 않습니다.
- 모순 검사는 같은 도구 단위입니다. 서로 다른 대상에 관한 상이한 판단도 충돌로 잡을 가능성이 있습니다.
- 결과 레코드 누락은 탐지와 재실행 대상 지정이 별개입니다. 규칙상 필요하지 않은 도구의 레코드만 빠진 경우에는 추가 요청이나 연결된 판단 ID가 없어 자동 복구 대상을 못 정할 수 있습니다.
- `category`나 `intended_use` 부족 경고만으로 질문이 자동 생성되지는 않습니다. 현재 질문은 종합 단계에서 도구의 `missing_information`을 바탕으로 생성합니다.

### 4.2 LLM 검토

[llm_agents.py](../palgijeone/llm_agents.py)의 `LLMVerificationAgent.verify()`가 규칙 검사를 먼저 실행하고, 그다음 전체 초안을 Gemini에 보냅니다.

프롬프트가 요청하는 검토는 다음과 같습니다.

- 상품 사실과 맞지 않는 도구 선택
- 결과 내부의 모순
- 근거 없는 판단
- 누락된 규제 검토 가능성
- 전체 결과의 완전성, 일관성, 추적 가능성

프롬프트에는 실제 법률 자문이나 새로운 법령 사실을 만들지 말라는 제한이 있습니다.
`is_mock=true`인 근거는 프로토타입 근거로 인정하도록 안내합니다.
따라서 검증 통과는 Mock 결과의 내부 검토를 의미하며, 실제 법적 타당성을 보장하지 않습니다.

LLM은 문제의 심각도(`warning` 또는 `critical`), 설명, 관련 판단 ID, 권장 조치를 반환할 수 있습니다.
빠진 도구에는 판단 ID가 없으므로 ID를 만들지 말고 `additional_tools_required`로 요청하도록 합니다.

### 4.3 규칙 결과와 LLM 결과 병합

1. 규칙 검증 이슈를 유지합니다.
2. LLM 이슈를 추가하되, 같은 `issue_type`과 `description` 조합은 중복 추가하지 않습니다.
3. 규칙과 LLM의 추가 도구 요청을 합치고 도구 이름 중복을 제거합니다.
4. 아래 우선순위에 따라 검증 상태를 계산합니다.

LLM이 "문제가 없다"고 답해도 규칙에서 발견한 critical 이슈를 지우지 않습니다.
또한 LLM 검토 요약이 긍정적이어도 추가 도구 요청이 남아 있으면 승인하지 않습니다.

## 5. 검증 상태와 분기 우선순위

LLM 모드의 병합된 검증 결과 기준입니다. 위 조건부터 먼저 적용됩니다.

| 우선순위 | 조건 | 내부 상태 | 파이프라인 동작 |
| --- | --- | --- | --- |
| 1 | 추가 도구 요청이 있거나 critical 이슈가 있음 | `revision_required` | 한도와 대상 도구를 확인한 뒤 재처리 |
| 2 | 위 조건이 없고 초안에 추가 질문이 있음 | `user_input_required` | 질문을 보존하고 종료 |
| 3 | 위 조건이 없고 이슈가 남아 있음 | `approved_with_warnings` | 경고와 함께 종료 |
| 4 | 추가 요청·질문·이슈가 없음 | `approved` | 종료 |

**질문과 critical 이슈가 동시에 있으면 재처리 조건이 우선합니다.**
"질문이 하나라도 있으면 무조건 즉시 중단한다"는 로직은 아닙니다.
최종적으로 `user_input_required`가 선택되었을 때 자동 재처리를 멈춥니다.

파이프라인에도 별도 방어 로직이 있습니다.
커스텀 검증기가 승인 상태와 추가 도구 요청을 동시에 반환하더라도,
추가 요청이 있으면 상태를 `revision_required`로 바꿉니다.

### 최종 출력 상태는 다른 필드입니다

| 내부 `verification.status` | 최종 `verification_status` |
| --- | --- |
| `approved` | `verified` |
| `approved_with_warnings` | `verified_with_warnings` |
| `user_input_required` | `incomplete` |
| 해결하지 못하고 종료된 `revision_required` | `incomplete` |

`overall_status`는 도구 결과를 종합한 위험·조치 상태이고, `verification_status`와 별개입니다.
예를 들어 `high_risk`이면서 `verified`일 수 있습니다.
이는 "위험하다는 결과가 현재 검증 규칙을 통과했다"는 뜻이지 판매 승인이 아닙니다.

## 6. 재실행 대상은 어떻게 정하는가

[pipeline.py](../palgijeone/pipeline.py)의 `_retry_tools()`가 다음 세 집합을 합칩니다.

1. `additional_tools_required`에 들어 있는 도구
2. 현재 결과에서 `selected=true`이고 `status=failed`인 도구
3. critical 이슈의 `related_finding_ids`에 연결된 판단을 만든 도구

중복 도구는 한 번만 실행합니다.
`additional_tools_required`에는 생략된 도구뿐 아니라 이미 실행한 도구도 들어갈 수 있습니다.
후자는 해당 도구의 재실행 요청으로 처리됩니다.

### 판단 ID를 도구로 연결하는 이유

검증 이슈는 "전파 판단 F-1에 근거가 없다"처럼 특정 판단을 지목할 수 있습니다.
파이프라인은 현재 초안에서 F-1의 `tool_name`을 찾아 해당 도구를 재실행합니다.
이때 F-1 한 항목만 고치는 것이 아니라, 도구가 반환한 전체 `ToolResult`를 새 결과로 교체합니다.

### 권장 조치와 실행 계획의 차이

`recommended_action`은 사람이 읽는 권장 조치이고, 실행 계획이나 코드가 아닙니다.
"검색어를 바꿔라", "근거를 보완하라"는 문장을 실행기가 해석하여 수행하지 않습니다.

critical 이슈가 있더라도 추가 요청, 실패 도구, 관련 판단 ID 중 어느 것으로도 대상을 찾지 못하면
`no_action_available`을 기록하고 `incomplete`로 종료합니다.
단순 warning에 연결된 판단 ID만으로는 재실행하지 않습니다.

### 재실행 입력

현재는 기존 `Product`와 `SelectionDecision(selected=True, reason=...)`을 전달합니다.
재처리 이유는 critical 설명들을 합치거나, 추가 도구 실행 요청이라는 문장으로 남깁니다.
제품 속성, 검색어, 외부 조회 조건을 자동으로 변경하지 않습니다.
현재 Mock 도구는 이 설명문에 맞춰 판단 로직을 수정하지 않습니다.

## 7. 종료 조건과 오류 처리

| 조건 | 처리 | trace에서 확인 |
| --- | --- | --- |
| 승인 또는 경고 승인 | 최종 결과 반환 | `verify`, `finalize` |
| 사용자 입력 필요 | 질문과 미완료 결과 반환 | `user_input_required` |
| 재처리 한도 소진 | 최신 결과를 유지하고 미완료 종료 | `stop_retry` / `exhausted` |
| 재실행할 도구 없음 | 미완료 종료 | `stop_retry` / `no_action_available` |
| 검증 호출 또는 응답 검증 실패 | 기존 도구 결과를 보존하고 미완료 종료 | `stop_retry` / `verification_failed` |

### 횟수 계산

기본값은 `max_remediation_attempts=2`입니다.

- 최초 검증: 1회
- 자동 재처리: 최대 2회
- 전체 검증: 최대 3회
- CLI LLM 모드의 정상 응답 기준 LLM 호출: 최초 선택 1회 + 검증 최대 3회 = 최대 4회

하나의 재처리 회차에서 여러 도구를 실행할 수 있습니다.
한도는 도구별 한도가 아니라 파이프라인 전체의 재처리 회차 한도입니다.
SDK 내부 네트워크 재시도는 이 계산과 별개이며, 실제 사용량 상한을 보장하는 숫자는 아닙니다.

한도는 Python 생성자에서 변경할 수 있습니다. 현재 CLI에는 한도 변경 옵션이 없습니다.

~~~python
pipeline = CompliancePipeline(max_remediation_attempts=1)
~~~

`0`이면 최초 실행과 검증까지만 수행하고 추가 도구 실행은 하지 않습니다.

### 검증 실패와 도구 실패는 다릅니다

도구 실행이 실패하면 실패 결과를 만들어 검증기에 전달하고, 재처리 대상으로 삼을 수 있습니다.
반면 검증 LLM의 타임아웃이나 응답 형식 오류는 검증 자체를 신뢰할 수 없는 상황이므로,
현재는 검증 호출을 자동 재시도하지 않고 종료합니다.

- 현재 초안에 없는 판단 ID: `invalid_verification_response`
- 그 외 검증 예외, JSON/Pydantic 응답 오류 등: `verification_failure`

검증 이슈의 `related_finding_ids`와 검증 결과의 `checked_finding_ids`가 현재 초안에 존재하는지 검사합니다.
이 검사는 critical뿐 아니라 모든 이슈의 참조에 적용합니다.
잘못된 ID를 조용히 무시하거나 엉뚱한 도구로 연결하지 않습니다.

검증 실패를 처리할 때 SDK 예외 원문 대신 예외 종류와 제한된 설명을 남깁니다.
이미 완료한 도구 결과와 이전 회차의 검증 결과는 유지합니다.
다만 최초 LLM 도구 선택과 결과 취합은 이 예외 처리 범위 밖입니다.
해당 단계의 오류는 `FinalAssessment`로 변환되지 않고 호출자에게 예외로 전달될 수 있습니다.

## 8. 상황별 실행 예시

다음 시나리오는 분기별 처리 과정을 설명합니다. B와 C는 의도적인 오류 주입 테스트를 기준으로 하며,
실제 외부 API나 LLM이 자율적으로 오류를 복구한 사례는 아닙니다.

### A. 필요한 도구가 빠진 경우

무선 상품인데 최초 분석에서 전파 도구를 생략했다고 가정합니다.

1. 최초 결과에 전파 도구의 생략 기록이 남습니다.
2. 규칙 또는 LLM 검증이 전파 도구 추가 실행을 요청합니다.
3. 전파 도구만 실행합니다.
4. 다른 도구의 결과는 유지하고 전파 결과만 교체합니다.
5. 전체 결과를 다시 취합하고 검증합니다.
6. 남은 문제가 없으면 승인, 질문만 남으면 사용자 입력 필요 상태로 종료합니다.

### B. 도구가 한 번 실패한 경우

테스트의 `FlakyTool`은 통관 도구가 첫 실행에서만 실패하도록 구성할 수 있습니다.

1. 최초 통관 결과는 `failed`입니다.
2. 검증이 도구 실패를 critical로 탐지합니다.
3. 통관 도구만 다시 실행합니다.
4. 두 번째 실행이 성공하면 최신 결과는 `success`로 바뀝니다.
5. 전체 결과를 다시 검증합니다.
6. 최초 실패 기록은 이력에 계속 남습니다.

이는 일시적 오류 복구 경로를 검증한 것이지, 실제 관세청 API 장애를 복구한 실험은 아닙니다.

### C. 판단에 근거가 없는 경우

테스트의 `MissingEvidenceOnceTool`은 첫 실행의 공통 판단에서 근거 목록을 지웁니다.

1. 규칙 검증이 `missing_evidence`와 해당 판단 ID를 반환합니다.
2. 판단 ID를 통해 해당 도구를 찾아 다시 실행합니다.
3. 테스트 래퍼가 두 번째 실행에서는 원래 Mock 근거를 유지합니다.
4. 전체 초안을 다시 검증합니다.

복구되는 이유는 테스트에서 두 번째 결과가 달라지도록 만들었기 때문입니다.
LLM이 실제 법령을 검색해서 근거를 새로 찾은 것이 아닙니다.

### D. 사용자 정보가 부족한 경우

RC 헬리콥터 샘플의 표시 연령과 사용 목적 관계처럼 추가 확인이 필요한 경우입니다.

1. 도구가 `missing_information`을 반환합니다.
2. 종합기가 이를 `follow_up_questions`로 만듭니다.
3. critical 이슈나 추가 도구 요청이 없다면 `user_input_required`가 됩니다.
4. 자동 재처리 없이 `incomplete`와 질문을 반환합니다.

현재는 사용자 답변을 받아 중단 지점부터 이어가는 기능이 없습니다.
CLI를 다시 실행하면 새 파이프라인 실행이 시작되며, 기본 샘플 자체는 변경되지 않습니다.

### E. 검증 자체가 잘못된 경우

LLM이 현재 초안에 없는 판단 ID를 반환하거나, 검증 호출에서 타임아웃이 발생한 경우입니다.

1. 검증 실패용 결과를 생성합니다.
2. 이전 도구 결과와 검증 이력을 유지합니다.
3. `verification_failed`를 기록합니다.
4. 규제 도구 재실행 없이 `incomplete`로 종료합니다.

### F. 반복해도 해결되지 않는 경우

같은 제품과 같은 Mock 로직이 같은 문제를 계속 만든다면 자동 재실행으로 해결되지 않을 수 있습니다.
현재는 결과가 달라지지 않았는지를 비교해서 조기 종료하지 않습니다.
재처리 한도에 도달하면 `exhausted`를 기록하고 종료합니다.

## 9. JSON과 실행 이력 읽는 법

| 필드 | 의미 |
| --- | --- |
| `tool_results` | 도구별 최신 결과. 정상 경로에서는 생략 도구 포함 6개 |
| `tool_result_history` | 최초 6개 기록과 모든 재실행 결과 |
| `verification` | 마지막 회차의 검증 결과 |
| `verification_history` | 회차별 검증 결과. 실패 결과 포함 |
| `verification_rounds` | 최초 검증을 포함한 검증 시도 횟수 |
| `remediation_history` | 실제 실행한 재처리 회차, 대상 도구, 사유, 상태 |
| `trace` | 입력부터 종료까지 시간순 이벤트 |
| `follow_up_questions` | 사용자에게 확인해야 할 질문 |
| `overall_status` | 도구 판단을 취합한 위험·조치 상태 |
| `verification_status` | 최종 결과의 검증 상태 |

통관 도구 하나만 한 번 재실행했다면 보통 다음과 같습니다.

- `tool_results`: 6개
- `tool_result_history`: 7개
- `verification_rounds`: 2
- `verification_history`: 2개
- `remediation_history`: 1개

이력의 `attempt`는 최초 기록이 1이고 이후 재처리 회차에 따라 2, 3으로 부여됩니다.
도구별 실제 실행 횟수와 항상 같지는 않습니다.
처음 생략되었던 도구의 첫 실제 실행도 재처리에서 실행되었다면 `attempt=2`일 수 있습니다.

이전 검증이 참조하는 판단 ID는 최신 결과가 아니라 이전 `tool_result_history`에만 남을 수 있습니다.
최신 `findings`만 보고 과거 검증의 참조가 잘못됐다고 판단하면 안 됩니다.
각 검증 시점에는 해당 시점의 초안 ID를 검사합니다.

`checked_finding_ids`는 정상 검증 결과 생성 시 코드가 초안의 모든 판단 ID를 넣습니다.
모델이 각 근거를 원문과 대조했다는 별도 증명이나 상세 점검 로그는 아닙니다.
전체 초안 스냅샷 자체는 매 회차 저장하지 않으며, 현재 실행 이력은 최종 JSON으로 반환되는 구조입니다.
DB 저장, 중단 후 재개, 실행 간 비교 기능은 미구현입니다.

## 10. 실행 및 결과 확인

아래 명령은 저장소 루트에서 실행합니다.
Git Bash에서는 경로에 `/`를 사용하고, PowerShell에서는 실행 파일 경로를 `.\.venv\Scripts\python.exe`로 바꿀 수 있습니다.

### 10.1 실제 LLM 실행

저장소 루트의 `.env`에 발급받은 API 키를 설정합니다. 키는 로컬 환경에만 보관합니다.

~~~bash
./.venv/Scripts/python.exe -X utf8 -m palgijeone.cli --product wireless_rc_helicopter --agent-mode llm
~~~

현재 기본 모델은 `gemini-3.5-flash-lite`이며, `--model`로 변경할 수 있습니다.
이 실행은 실제 외부 LLM 요청을 발생시킵니다.
모델 사용 가능 여부, 무료 한도와 비용은 프로젝트 설정 및 제공자 정책에 따릅니다.
검증 결과는 모델 응답에 따라 달라질 수 있으므로 동일한 종료 상태를 보장하지 않습니다.

현재 CLI는 실시간 스트리밍 로그가 아닙니다.
실행이 완료된 후 단계별 trace와 최종 요약을 한꺼번에 출력합니다.

### 10.2 긴 결과를 파일로 저장

~~~bash
./.venv/Scripts/python.exe -X utf8 -m palgijeone.cli --product wireless_rc_helicopter --agent-mode llm --json > result.json
~~~

- 위 명령은 기존 출력의 저장이 아니라 새 LLM 실행입니다.
- 리다이렉션 때문에 터미널에 JSON이 표시되지 않는 것이 정상입니다.
- 같은 파일이 있으면 덮어씁니다.
- 파일에서 `trace`, `verification_history`, `remediation_history`를 먼저 확인합니다.
- 실행 실패 시 파일이 비거나 불완전할 수 있으므로 성공 여부도 확인합니다.
- 생성한 JSON에는 제품 정보와 오류 내용이 포함될 수 있으므로, 저장소에 추가하기 전에 민감정보 포함 여부를 확인합니다.

### 10.3 API 없이 재처리 테스트 실행

~~~bash
./.venv/Scripts/python.exe -B -X utf8 -m unittest discover -s tests -p test_remediation.py -v
./.venv/Scripts/python.exe -B -X utf8 -m unittest discover -s tests -p test_pipeline.py -v
~~~

이 테스트들은 실제 Gemini를 호출하지 않습니다.
응답을 정해둔 가짜 클라이언트와 의도적인 오류 주입으로 분기를 재현합니다.
명령 출력은 테스트 이름과 성공·실패이며, 단계별 CLI trace 화면은 아닙니다.

실제 LLM 실행은 분석·검증 호출의 연결을 확인하는 방법이고,
오류 주입 테스트는 자동 재처리 분기를 재현하여 확인하는 방법입니다.
기본 샘플만 실행했을 때 재처리 0회여도 오류가 아닙니다.

## 12. 수집·소관별 판단 모듈과의 연계

이 절은 **현재 구현에 포함되지 않은 확장 설계 고려사항**을 정리합니다.

현재 검증·재처리 구조는 수집 또는 소관별 판단 모듈의 결과를 검사하는 계층으로 활용할 수 있습니다.
다만 현재 도구는 수집과 판단이 함께 들어 있는 Mock이므로 연계 시 각 모듈의 책임과 데이터 계약을 정의해야 합니다.

| 설계 항목 | 현재 | 확장 방향 |
| --- | --- | --- |
| 결과 계약 | `ToolResult`와 공통 `RegulatoryFinding` | 소관별 판단을 공통 검증 입력으로 변환 |
| 근거 추적 | 출처 필드와 판단 ID | 법령 버전, 조회 시각, 적용 범위, 제품 사실 연결 |
| 재처리 단위 | 도구 전체 재실행 | 인식 보완, 근거 재수집, 소관 재판단 등으로 구분 |
| 사용자 정보 부족 | 질문 반환 후 종료 | 답변 반영, 영향받는 결과 무효화, 부분 재개 |
| 진전 없는 반복 | 횟수 한도로 중단 | 동일 문제 반복 탐지와 수동 검토 전환 |
| 상태 표현 | 위험도와 검증 상태 분리 | 수입·판매·표시 결과와 검증 상태의 의미 합의 |

재처리 계획을 확장한다면 "어떤 도구를 다시 부를지"에 더해
"무엇이 부족하고, 어떤 입력이나 근거가 달라져야 하는지"를 구조화해야 합니다.
권장 조치 설명문을 붙이는 것만으로는 실제 개선 동작이 만들어지지 않습니다.

## 13. 데이터 및 보안

- `.env`, 실제 API 키, 키가 보이는 터미널 캡처는 공유하지 않습니다.
- LLM 모드는 제품 정보와 전체 검증 초안을 외부 모델 제공자에게 전송합니다.
- 테스트에는 샘플 상품을 사용합니다. 실제 상품 정보나 민감한 원문을 사용하는 경우 외부 전송 허용 범위를 먼저 확인합니다.
- 검증 서비스 예외는 메시지 원문을 숨기지만, 규제 도구 예외는 현재 `ToolResult.error`에 원문을 저장합니다.
- 따라서 모든 오류·로그·JSON이 자동으로 비밀정보를 제거한다고 가정하면 안 됩니다. 실제 API 연결 전 별도 마스킹이 필요합니다.
- `not_applicable`은 현재 선택 생략 기록이고, `verified`는 프로토타입 검증 통과입니다. 두 상태는 법적 면제나 판매 승인을 의미하지 않습니다.
